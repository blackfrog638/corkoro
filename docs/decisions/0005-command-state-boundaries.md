# 命令状态、事务与证明边界

日期：2026-11-11

状态：采用为实现约束；由状态机审查细化既有契约。尚无业务实现，不代表已完成文件系统事务或并发验证。

## 发现

原契约的“完整校验”“原子替换”“失败不变”不足以分别描述配置编辑、构建检查、并发写入和提交后响应丢失。旧 check/plan 结果也不能保证构建时仍是相同输入。

## 决策

1. 区分配置结构校验、命令局部前置条件和完整构建校验。list/remove 不以源文件存在或引用有效为前提；结构损坏仍须先修复。
2. 合作写入者串行化同一实际配置的读取到提交；复核版本并原子提交。不支持手工编辑器/同步软件与命令并发写同一配置，不能声称哈希复核可消除全部竞争。
3. check/plan 是观察，不是持久许可；构建必须自行捕获输入，检查与渲染消费同一批字节。多文件瞬时快照不在当前承诺中。
4. 区分提交前失败和提交后响应未知。后者通过重新读取状态和幂等请求恢复，不承诺任意失败都没有副作用。
5. 构建先暂存再提交；失败不破坏当前有效版本。完整提交协议及 Windows 文件操作需要实际验证后才能宣称成立。
6. 稳定 ID 在保留清单历史的条件下保证；彻底手删后复用旧 ID 无法由当前配置检测。remove 不删除旧产物、不撤回远端。

## 证据与限度

[状态机、归纳论证和反例](../state-machine.md) 明确假设、证明对象与未覆盖能力。[有限模型](../../tools/verification/cli-state-machine.mjs) 可枚举抽象状态与并发交错；它不是 CLI 实现测试，也不是无限状态的机器证明。预留远端命令仍需单独定义状态机。
