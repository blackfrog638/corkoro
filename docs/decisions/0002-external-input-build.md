# 外部输入、构建规划与部署边界

日期：2026-11-11

状态：已接受。根据本轮对话更新，尚未实现运行时能力。

最新调整：[单配置与纯生成站点](0004-vault-config-generated-site.md) 覆盖用户站点项目与外部定制源码的安排。输入放在 Vault，输出为纯生成站点，首版使用内置默认主题。

后续细化：[发布清单决策](0003-publication-selection.md) 明确外部输入中的授权清单，以及陌生 Vault 的发现与选择流程；公开标记的位置和 ID 保存方式以该决策为准。

## 背景

用户希望原始 Markdown、资源和站点配置不放进发布工具源码，而是通过 CLI 参数及配置指定。Obsidian 插件调用工具完成发布，借鉴 GN/Ninja 的生成与执行分工。

## 决策

1. 分开工具开发仓库、用户内容与站点项目、生成产物。生产输入在外部；人工测试样例及文档示例可留在工具仓库。
2. CLI 为桌面插件、agent 和 CI 的统一入口。插件收集配置和必要的编辑器元数据，展示诊断；不生成任意 shell 脚本，不复制核心依赖分析逻辑。
3. 核心内部区分配置解析、构建规划、执行。初期在一个 CLI 中运行，不另建 GN/Ninja、不提前实现通用任务图调度或持久化执行计划。
4. 配置文件目录是配置内相对路径的基准；对应 CLI 参数覆盖配置。源文件默认只读，输出与源文件目录隔离。
5. 构建产生公开内容包和网站，不产生远端发布或发信副作用。部署显式消费已构建产物，并跟踪其真实发布状态。
6. `apps/web` 提供默认 Astro 渲染能力，通过配置消费外部内容包和用户站点定制；用户改样式和页面不应要求修改工具源码。
7. 不再把仓库根目录 `content/published` 定义为固定输入或输出位置。使用 `examples/site` 解释用户项目结构，输出路径由配置指定。

## 保留的约束

显式公开标记、稳定文章 ID、未公开内容隔离、匿名评论审核规则及技术方向继续沿用前一份 ADR。Obsidian 语法支持不等于依赖 Obsidian 应用运行。

## 后果与验证

需要校验外部路径、输出所有权和配置格式版本；CLI 需能在不同工作目录下得到相同结果。使用 Windows 含空格和中文路径的样例验证参数传递；用源文件哈希证明构建未改写输入。

移动端不能假设有本地 CLI。未来如需要移动发布，可增加远端构建适配，仍使用同一配置和内容协议。独立发布包的分发方式、完整主题覆盖 API、缓存和持久化计划留到对应里程碑，不在本次提前建设。
