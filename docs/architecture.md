# 架构

本文描述目标架构。当前实现状态见 [开发计划](roadmap.md)。

## 数据流

```text
Obsidian 插件（Vault 适配） ─┐
                           ├→ 共享发布核心 → 公开内容包 → GitHub → Actions → Astro → Pages
CLI / agent（文件系统适配）─┘

访客 → 网站评论组件 → Worker API → D1
管理员 / agent → 管理命令或受控 API → 审核记录
```

文章读取不依赖评论服务。网站样式变化不要求插件更新。发布核心可在关闭 Obsidian 时运行和测试。

## 模块职责

- `apps/web`：消费经过校验的公开内容，渲染文章、搜索和交互界面。不得读取私人 Vault 或数据库管理凭据。
- `apps/api`：接收访客请求、执行权限与运行时校验、管理评论状态。D1 只能通过服务端或授权管理工具访问。
- `apps/obsidian-plugin`：选择文章、提供发布入口、展示计划及结果。读取 Vault 的逻辑在此适配，不进入核心。
- `packages/publisher`：解析源文档、选择允许发布的内容、解析链接和附件、生成内容包、编排发布过程。文件读取和部署传输留在适配边界。
- `packages/content-contract`：内容包的字段、版本、校验与兼容性说明。不包含站点主题逻辑。
- `packages/api-contract`：分别描述公开请求、公开返回和管理操作，禁止公开模型直接复用数据库整行记录。
- `tools/cli`：终端入口，供开发者与 agent 调用；不复制发布规则。

## 内容边界

源笔记位于仓库外的用户 Vault，开发时使用 `tests/fixtures/vault`。生产 Vault 路径通过本地配置指定。

目标内容包由 Markdown、附件和 `manifest.json` 构成。至少需要格式版本、文章稳定 ID、slug、文章路径和附件清单。具体字段及解析实现尚未冻结，在第一条发布链路中确定。

只导出 `publish: true` 的文章。附件必须位于允许发布的集合。嵌入未公开笔记、链接重名文件、路径越界及缺失附件应产生明确诊断，不能静默扩大发布范围。撤回文章与旧附件清理需要在内容包协议中明确；初次实现前以 [开发计划](roadmap.md) 的待定事项为准。

## 评论边界

访客填写昵称、邮箱和正文，无账户、无邮箱验证码。服务端创建 `pending` 记录，管理操作可批准或拒绝。公开读取只返回批准记录的公开字段。文章关联使用稳定 ID，不使用可变标题。

邮箱只作内部联系方式，不能用作已验证身份、修改权限或自动订阅依据。管理操作仍需认证授权，免登录仅针对访客评论。

## 发布与订阅

内容上传、构建、部署是不同状态。发布成功应以对应版本的部署结果为依据，失败时保留诊断信息。重复调用、撤回语义及部署状态关联在发布流程实现时验证。

RSS 可随文章静态生成。邮件订阅是独立流程，供应商、邮箱确认和通知频率尚未确定；未确定前不实现发送。若未来自动通知，以成功部署的版本为触发依据并防止重复发送。

## 环境与管理

本地、预览和生产配置分开；MCP / Wrangler 用于管理员和 agent。常规审核封装成范围有限的命令，记录操作对象和结果。真实凭据留在本地安全配置、CI Secrets 或平台密钥管理中。
