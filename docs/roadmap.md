# 开发计划

更新：2026-11-11。本文是接下来开发的顺序与验收依据，不表示这些功能已完成。

## 当前状态与依据

仓库仅有说明文件、根包清单和工作区配置，无应用依赖、锁文件、业务实现、CLI、测试或 CI。依据为 [架构](architecture.md)、[初始决策](decisions/0001-project-boundaries.md) 和 [外部输入决策](decisions/0002-external-input-build.md)。

本轮完成文档及目录约定调整，不实施下面的业务计划。各阶段按依赖推进，第一阶段不需要真实 Vault、云账号或域名。

## 目标与边界

外部配置指向原始笔记和资源，独立 CLI 生成公开内容包并驱动 Astro 构建。用户无需把文章复制进工具源码，Obsidian 关闭时也可执行；插件后续复用 CLI。构建与部署分离。

先做纵向可验证的最小流程，再加入部署、评论和编辑器体验。不实现通用任务图引擎、任意 shell 任务、持久化构建计划、增量缓存或移动构建服务。邮件订阅单独规划。

## 第一阶段：配置协议与只读检查 CLI（建议下一次执行）

**交付范围**：`packages/content-contract` 定义版本化 JSON 配置和诊断；`packages/publisher` 负责配置归一化与路径检查；`tools/cli` 提供真实 `check --config ... --json` 入口。`examples/site` 加入不含私人信息的示例，测试输入继续由人工生成。

**实现顺序**：

1. 核对届时依赖兼容性，固定 Node 和 pnpm，建立必要的包清单、锁文件、TypeScript 及测试入口。仅安装这条链路需要的依赖。
2. 定义配置版本、内容根目录、格式（Markdown / Obsidian Markdown）、附件查找范围、输出目录及基本站点字段。禁止未知配置键掩盖拼写错误；密钥不属于可公开配置。
3. 固定路径规则：`--config` 按调用者目录定位；配置字段和对应 CLI 路径覆盖值按配置目录解析。所有路径字段采用一致基准，包括附件目录。
4. 检查输入存在性、输出与输入隔离、符号链接实际目标及配置版本；此阶段不生成站点、不改源、不连接云端。
5. 给出明确成功/失败退出码；JSON 模式 stdout 只输出结构化结果，日志写 stderr。首次确定格式后建立测试。

**验收**：从仓库目录和另一个临时目录使用同一个绝对配置路径调用，结果一致；包含中文和空格的路径成功；相对路径与 CLI 覆盖符合规则；无效配置、输出覆盖源目录和越界路径明确失败；源目录哈希前后不变。通过独立临时目录验证，不只在固定仓库样例位置测试。

**不包含**：Astro 安装、文章转换、部署、评论、插件。通过这一阶段后再进入内容执行。

## 第二阶段：公开内容包与内容执行

**依赖**：第一阶段。涉及 `packages/content-contract`、`packages/publisher`、`tools/cli` 与人工笔记样例。

- 冻结内容包 manifest 第一版：格式版本、稳定 ID、slug、文章文件及附件映射。ID 首版建议显式填写，缺失时报错；不自动写回笔记。这是实施默认方案，若需自动分配再单独确定写回方式。
- 核心内先规划公开文件与引用关系，再执行写出；检查与执行复用相同规则，不让插件维护文件依赖。
- 首批支持标准 Markdown、Obsidian 双链/别名与图片引用；标题链接、Callout、公式按样例加入。块引用、整篇嵌入和插件生成视图先明确诊断，避免承诺完整 Obsidian 兼容。
- 定义输出文件所有权和失败处理：首次拒绝覆盖不属于工具的既有文件；后续仅清理上次 manifest 记录的旧产物。校验失败不破坏上次有效产物。
- 增加真实内容测试与检查命令，更新 runbook。

**验收**：只包含公开文章及其允许的附件；未公开笔记及无引用附件不出现；重复 ID/slug、缺失及重名链接、越界引用明确失败；相同输入产生相同内容包；改名保留 ID；撤回文章和无引用旧附件从新产物移除；输出中无本地绝对路径，失败不修改源或破坏旧结果。

## 第三阶段：最小 Astro 渲染与外部定制

**依赖**：第二阶段。涉及 `apps/web` 和 CLI 的构建适配。

- 默认渲染器消费外部内容包，生成首页、文章页、基础导航和 Pagefind 搜索。
- 将内容包路径、站点 URL / base 路径、外部样式接入配置；不得写回工具源码里的内容目录。
- 首先证明外部 CSS 可覆盖设计变量和排版；再定义文章布局/页面覆盖接口，保持用户定制文件位于用户站点项目。默认主题不绑定最终视觉方案。
- CLI `build` 编排内容执行和网站构建。内容检查、类型检查、测试和构建入口真实可用后接 CI。

**验收**：在工具仓库外创建站点项目并构建到独立输出；改外部样式影响页面且工具源码不变；首页、文章、附件、搜索在桌面及移动宽度可用；根路径与项目子路径正确；无 Obsidian、无云密钥也能构建。CI 使用人工样例，不接触私人 Vault。

## 第四阶段：部署适配与状态跟踪

**依赖**：第三阶段；接入前需要用户的 GitHub 仓库、Pages 基路径或域名。

- 选择本地与 CI 的产物交接方式，使用可移植配置和获准公开的快照；不把整个 Vault 上传到 GitHub。
- `deploy` 接受明确构建产物或构建版本，记录上传、构建（若有）、发布结果；`status` 返回同一版本的状态。
- 确定产物保存、撤回与重试规则，防止旧构建覆盖较新的发布；凭据留在管理环境。

**验收**：在授权预览目标中完成一次发布；模拟失败可定位阶段；上传完成不误报部署成功；重试不产生内容重复；本地 `build` 始终无远端副作用。

## 第五阶段：匿名评论与管理命令

**依赖**：稳定文章 ID 和最小网站；接入云端前需要 Cloudflare 目标环境。

- 建立 Worker/D1、本地迁移和公开/管理数据协议；访客填写资料直接提交，服务端固定待审。
- 提供列出、批准、拒绝和导出命令，可由 agent 操作。授权机制与审计在此实现，不要求先做管理网页。
- 实现输入校验、提交频率限制、公开字段隔离和必要的反垃圾措施。

**验收**：匿名不能审核，待审内容不可公开，邮箱不泄露；获批后显示且与文章改名无关；迁移、导出和恢复在测试环境跑通。MCP/CLI 限定环境和操作范围。

## 第六阶段：Obsidian 桌面入口及后续订阅

**依赖**：CLI 构建、部署和状态接口稳定。插件可与评论阶段独立推进，不等待评论实现。

- 插件收集配置、展示诊断、调用 CLI；可执行文件和参数分开传递。未保存笔记的处理策略在插件设计时明确。
- 增加 CLI 版本兼容检查与真实状态展示；没有 CLI 时给出可操作说明，不能悄悄切换到另一套发布逻辑。
- RSS 可在渲染阶段就加入；邮件订阅要另行明确服务商、确认、退订及发送频率，再开发。移动发布另议。

**验收**：插件与终端对同一输入产物一致，失败信息可定位；改网站主题无需更新插件；关闭 Obsidian 后 CLI 仍可执行。

## 计划置信度与本次验证

模块位置和约束来自当前仓库及已接受的对话决策；第一阶段可直接开始。版本化字段、依赖版本、Astro 外部布局扩展方式尚未通过原型验证，在对应阶段核实，不能视为已完成接口。

本次只检查文档链接、目录引用、示意 JSON 语法和过时约定，无业务代码变化，不运行或声称通过不存在的构建和测试。
