# 桌面 CLI 跨平台实施计划

2026-11-18 排期。当前最高开发优先级，首个交付项是三平台只读 CLI 基线。共用 CLI 用例和 CI 矩阵已实现，Linux、macOS 写入适配待开发。开发顺序见[路线图](roadmap.md)，实测范围见[运行手册](runbook.md)，适配边界见 [ADR 0015](decisions/0015-cross-platform-cli.md)。

## 用户需求与完成条件

用户应能把使用相对路径的人工 Vault 连同站点配置复制到另一台电脑，在 Obsidian 关闭时用同一套 CLI 扫描、选择、检查、构建并预览博客。文章与页面沿用配置中的稳定 ID，公开范围、站内路由及诊断含义在三个系统上一致。带有 Windows 跨盘绝对路径的配置迁移时，由用户重新指定对应的本地位置。

按操作系统、实际文件系统和能力分别验收。Windows 已验证环境为本地固定 NTFS 卷，新增写入的首批目标为 Linux 本地 ext4 和 macOS 本地 APFS。一次本地流程完成于预览可访问、公开快照可核对。远端上传和 Pages 上线另按部署流程操作。

## 第一项变更 · 三平台只读基线

1. 扩展 [CI 工作流](../.github/workflows/ci.yml)。保留现有 Windows 全量任务，在 Ubuntu 和 macOS 原生 runner 上按仓库固定的 Node、pnpm 和锁文件安装，核对实际 Node 版本，执行类型检查、编译及只读 CLI 测试。Windows 也执行同一套只读断言。
2. 复用[人工 Vault](../tests/fixtures/vault) 和[现有 CLI 测试](../tests/runtime/cli.test.mjs)。把样例复制到含中文和空格的临时路径，从两个不同的工作目录，用参数数组调用编译后的 CLI。对 `inspect` 传入绝对源目录，对 `content list`、`check`、`plan` 传入同一绝对配置路径，并读取真实退出码与 JSON 结果。
3. 三平台使用同一组期望值。已选样例应得到两篇文章、一页及头像和正文图片各自的依赖来源；有公开属性但未选择的笔记仍然私有。空清单的 `plan` 退出 0 且 `buildable=false`，含未获授权引用的样例退出 3。对比稳定 ID、路由、诊断码和资源集合，主机绝对路径按各自临时目录核对。

**通过条件**为三个任务都实际执行这些用例，运行前后 Vault 文件清单与字节摘要相同，配置的输出目录没有被创建。CI 日志列出各平台已执行及跳过的测试。在此阶段继续检查非 Windows 事务写入返回 `TRANSACTION_UNSUPPORTED`，Windows 继续运行完整站点验收。

## 第二项变更 · Linux 本地事务与构建

1. 在 [openTransaction](../packages/publisher/src/transaction.ts) 内选择平台后端。公共层继续处理配置解析、版本复核、取消、临时文件所有权及结果封装。Windows 后端沿用现有 PowerShell/.NET 实现。Linux 后端先确认目标所在卷，再选择并实测进程退出即释放的非阻塞锁、同卷原子替换和仅在目标不存在时创建的原语。若需要辅助程序，在此阶段确定分发方式并测试 CLI 父进程退出后的释放行为。
2. 以本地 ext4 验证下表，记录实际卷类型。锁载体位于受管理的 `.corkoro-state` 内，按配置父目录身份与文件名定位。确认私有配置和临时副本的访问权限，以及替换前后的权限处理。卷类型或锁与提交语义无法确认时，继续返回不支持。
3. 对配置、[独立内容包](../packages/publisher/src/bundle.ts)和[站点版本指针](../apps/web/src/index.ts)分别运行对应的真实入口。完整 `build` 从同批捕获字节生成站点，最后切换一次 `site.current.json`。Linux 写入测试通过后，在同一平台执行下文的整站验收。

| 事务场景 | 在目标文件系统上应观察到的结果 |
| --- | --- |
| 并发初始化、竞争更新 | 并发 `init` 最多创建一份配置。持锁期间第二个写入者立即得到 `CONFIG_BUSY` 或 `OUTPUT_BUSY`。持有者退出后可再次取锁。 |
| 配置生命周期 | 初次清单为空。重复添加和停用保持幂等，源已缺失仍可停用。ID、slug、页面、资料、友链及主题得以保留，正文与附件摘要一致。 |
| 取消、进程中断、提交响应丢失 | 提交前失败或取消保留旧版本。强杀后读到完整旧版或新版。提交结果无法判定时返回退出 5、`effect=unknown`，调用方重读配置、内容包或站点指针后再决定是否重试。 |
| 路径与所有权 | 用目录符号链接、硬链接、目录被改名及不同路径别名验证文件身份与输入输出隔离。已有陌生输出保留；遗留临时文件遵循原有恢复协议。 |

事务阶段、错误及恢复规则以[配置事务协议](config-transactions.md)、[内容包提交决策](decisions/0009-public-content-bundle.md)和[站点提交决策](decisions/0011-generated-site-publication.md)为准。这里验收进程中断，断电耐久性另议。

## 第三项变更 · macOS 本地事务与构建

在本地 APFS 上复用已通过的事务用例，针对卷差异补测。当前锁名对整个目标路径调用 `toUpperCase()`。实现时需按实际卷的文件名规则定位锁，特别是配置尚不存在、尚无目标文件身份可比对的并发 `init`。

- 先在默认大小写不敏感 APFS 上，用大小写别名及 Unicode 组合形式的文件名访问同一配置，验证两个进程竞争同一把锁。
- 再在大小写敏感 APFS 卷上验证可共存的文件名各自定位到正确配置，同时沿用内容契约的路由冲突规则。例如两篇源笔记的文件名可区分，冲突的公开路由仍应由 `check` 报告。
- 记录 runner 架构、卷类型、大小写模式和实际执行的事务用例。每种通过的卷模式单独更新支持记录，随后在已验证模式运行整站验收。

## 每个新增写入平台的整站验收

扩展 [verify:sites](../tools/verification/sites.mjs) 的 Windows 平台断言，使它能在已接入的目标卷上执行。核对生成项目到 Astro 依赖目录的链接、Astro 子进程的工作目录、Pagefind 索引和预览 HTTP 响应。CI 使用人工内容及临时输出目录。

| 人工配置 | `corkoro build` 及后续检查 |
| --- | --- |
| `selected.config.json` | 退出 0。文章、关于页和获准资源可访问，搜索索引可用。预览逐文件核对站点指针记录的摘要，`package:site` 生成的公开快照能通过校验。 |
| `pages-only.config.json` | 退出 0。零文章仍生成关于页，导航和页面资源可访问。另在临时副本设置完整 `site.address`，使用示例 origin 和 `/blog/` 基路径，验证带前缀的页面、资源和搜索地址。 |
| `corkoro.config.json`、`blocked.config.json` | 空选择、未授权引用分别退出 3。首次失败不产生有效指针；已有有效站点时，另测失败后原版本仍可读取。 |

在不同工作目录以同一份配置重建，核对内容包的稳定 ID、路由、获准资源和 `buildId`。各平台的随机版本目录按各自指针解析。构建前后核对 Vault 清单及摘要，确认预览和快照只含当前公开文件。用真实 `preview` CLI 启动服务，读取其 JSON 中的地址，核对 HTTP 响应，停止进程后确认端口已释放。

每阶段合入时，在[运行手册](runbook.md)登记实际命令、系统与卷、运行记录、通过项及跳过项。三平台的只读流程，以及三个目标系统各自已声明支持的本地卷上的配置写入、内容包提交、构建和预览全部通过后，路线图才将本项标为完成。
